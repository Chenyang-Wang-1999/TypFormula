# 会议纪要：公式编辑原型的当前算法与架构

> 阶段收尾（2026-09-09）：用户决定公式原型到此为止。本文已统一到当前实现，补充宏管理器、嵌套模板、缓存更新和验证记录；历史方案仅作为决策演变说明。操作入口见 [README](README.md)。

范围：`prototypes/lyx-rust` 独立公式原型  
记录依据：本轮讨论、当前源码及用户试用反馈。

本纪要重点记录决策依据，而不仅是功能清单。各项说明围绕“遇到的问题 → 采用的方案 → 为什么这样选 → 接受的代价”展开。明确区分用户已经确定的原则、原型阶段的工程取舍和尚未实施的建议。

## 一、已确定的设计原则

1. 采用 LyX 风格的结构化编辑：对象有明确的输入槽，键盘负责进入、退出和切换槽位。编辑时重视结构清楚和操作顺手，不要求与最终排版像素一致。
2. 文件输入输出使用 Typst 源码，不增加自定义文档格式。编辑树、光标、SVG、查询缓存都是内存状态，不作为另一份文档保存。
3. Rust 管理编辑结构和编辑行为；Typst 负责未知表达式的语义及附件布局策略；浏览器负责显示、实际坐标计算和测量。
4. 普通输入保持简单，不通过字典自动合并或替换对象。结构化解析发生在命令确认、源码导入等明确的入口。
5. 宏使用原生 Typst `#let`，不另设宏语言、创建来源标记或文件格式。按结构分析判断可展性：可展宏保存调用、仅展开显示，并提供共享参数槽；不可展内容保留源码交给 Typst。编辑器不实现任意 Typst 代码的求值。

当前原型一次处理一个公式及其前置 `#let` 定义。早期讨论的“代码块包含多个公式”的完整文档编辑器，不属于当前原型已经完成的能力。

“原生 Typst”也不等于逐字保留整个输入文件：Raw、字典节点保留各自源码，已识别的结构则按规则重新序列化。例如 `a/b` 可导出为 `frac(a, b)`，空格和分组形式也可能变化。

### 核心决策及理由

| 决策点 | 问题与推导 | 决定及其代价 |
|---|---|---|
| 结构编辑还是最终效果预览 | 用户更重视 LyX 式的槽位和键盘操作，最终排版一致性不是首要目标 | 以结构化编辑为主；显示可以近似，但必须清楚地表达对象关系 |
| 是否另存编辑器格式 | LyX 格式与可供 AI 使用的源码双份保存，会增加同步和出错机会 | 文件只保存 `.typ`，编辑状态留在内存；重新打开时要从源码重建结构 |
| 是否完整移植 LyX | 早期原型的输入不够顺手，因此转向借鉴 LyX 的编辑树和键盘逻辑；最终又明确移除部分机制 | 沿用有价值的交互逻辑，不以保留 LyX 全部类型为目标；当前也不能称为全量一比一移植 |
| 宏是否由编辑器展开 | 曾删除本地宏机制以明确 Raw 边界；宏管理阶段需要恢复参数槽，又不希望引入第二套语义 | 按可展性自动分类，保存调用和一份实参，仅在视图中展开；不可展调用仍是 Raw，任意代码求值留给 Typst |
| 可扩展性放在哪里 | 把所有符号显示关系硬编码进 Rust 不便维护，但让配置介入普通输入又会产生意外转换 | 先把显示映射外置为字典；这还不是任意结构模式的通用扩展系统 |

“宏多槽同步”现已通过共享实参槽实现；“完整代码块包含公式”仍属于未来文档编辑器，未纳入本原型。

## 二、三个运行部分

| 部分 | 职责 | 运行位置 |
|---|---|---|
| Rust 编辑核心，编译为 `web/core.wasm` | 编辑树、宏登记与模板投影、解析与序列化、输入状态、光标、选区、撤销 | 浏览器 |
| `lyx-typst-demo.exe` | 提供网页与 API，调用 Tinymist 和附件适配器 | 本机 |
| `lyx-typst-layout-adapter.exe` | 调用固定版本 Typst 内部库，判断附件位置并处理 stretch | 本机 |

`wasm32-unknown-unknown` 是 Rust 的 WebAssembly 编译目标名称，不是第四个程序。浏览器加载 WASM 后，同步执行 Rust 编辑逻辑。

适配器独立编译，避免把完整 Typst 求值、字体和布局依赖带入 WASM。每个附件请求使用独立进程，原生服务可以在超时时结束进程。

**为什么这样拆分：** 浏览器适合快速构建和调整编辑界面，Rust/WASM 则让关键编辑操作继续由 Rust 同步执行；这样调整视觉不必同时重写编辑核心。完整 Typst 求值和布局使用原生程序，可以复用现成的编译器依赖，并处理字体与进程超时。

**哪些是原则，哪些是临时取舍：** “编辑与语义求值分工”是当前架构原则；“原生服务和适配器恰好是两个 exe”“每次查询新建进程”是可替换的实现方式。它们便于隔离依赖和中止超时，但增加启动开销，也不能跨请求保留该进程的内部缓存。日常构建入口因此应统一，不能要求用户理解所有内部产物才能使用。

## 三、编辑树与输入状态

### 3.1 数据结构

`MathData` 是 `MathAtom` 数组；结构对象通过 `cells` 持有子数组。光标使用 `CursorSlice` 路径描述所在槽位，并用 `pos` 描述槽内插入位置。

例如：

```text
Script
├─ 中心槽：Raw("lim")
└─ 下标槽：Char('x')、Raw("->")、Raw("oo")
```

上例是未配置箭头和无穷符号映射时的示意。Raw 或 Symbol 的区别不影响外层 Script 的成立。

当前结构包括普通字符、保留源码的显示符号、Raw、字符串、分式、平方根与带指数根式、上下标、括号、矩阵、多行对齐、装饰，以及未确认命令草稿、可展的 `MacroCall`。希腊字母主要通过显示字典形成 Symbol。模板中的 `Parameter` 和 `TemplateCall` 是派生节点，不进入公式源码树或导出文件。

**为什么用树和槽位：** 分子、分母、根指数、上下标都有天然的结构位置。用树可以直接表达“进入分母”“退出一层”“删除外层但保留当前槽”，比在扁平字符串上猜括号范围更适合 LyX 式操作。光标首先是结构路径，显示坐标可以随后变化而不丢失编辑位置。

**保留结构的标准：** 分式、根式、上下标等值得拥有可进入的槽位；普通符号通常只需要看见和整体操作，无需为了每个符号增加一种编辑结构。

### 3.2 普通输入

- 普通字符逐个插入，不合并相邻运算符。例如直接输入 `<=+`，得到三个字符节点。后续补充：显示层可以查询单字符键，改变字形，但不改变 Char 对象或源码。
- 保留 `/`、`^`、`_` 的结构快捷键。`/` 把选区或左侧对象放入分子，进入分母；`^`、`_` 创建或进入上下标槽。
- `\` 开启命令模式；`"` 开启字符串模式。
- 普通公式中的空格可退出当前结构，Tab 切换槽位；方向键按结构进入、退出或切换。

**为什么普通输入不做对象转换或合并：** 用户测试发现输入 `<=` 后再输入 `+`，相邻对象可能被合并并整体编译，操作结果超出了这次按键本身。决定让普通输入只处理本次字符，避免为了识别命令回头改写已输入对象。

**为什么仍保留 `/`、`^`、`_`：** 这是用户明确选择的例外。它们是创建分式和上下标的直接结构动作，操作目标清楚；与后台把若干普通字符重新识别成另一个对象不同。简化输入不意味着取消已经顺手的结构快捷键。

### 3.3 命令模式

1. 使用 `Unknown` 节点保存草稿文字、草稿光标、选区和取消时需要恢复的原内容。
2. 空格、括号和反斜杠保留在草稿中；左右键只移动草稿光标，不自动提交。
3. 只有 Enter 确认命令。Tab 或点击补全候选只填入文字。
4. 对 `frac`、`sqrt` 等确切结构模板，可直接创建空槽；完整表达式交给 Typst 语法解析器，再投影为编辑树。
5. Esc 取消草稿并恢复原内容；语法尚未完成时继续保留草稿和错误提示。

补全来自 Tinymist LSP，并保留少量本地结构模板。字典不参与补全。当前补全请求使用约 120 ms 防抖、单个在途请求，并为每次投影启动独立 LSP 会话；这是针对先前发现的旧文档快照问题所作的实现选择。

**为什么只能 Enter 确认：** Typst 表达式本来就需要空格、括号和反斜杠；把这些字符同时用作“结束命令”会截断用户正在输入的源码。左右键也只应移动草稿光标。以 Enter 为明确提交边界，用户可以完整写完表达式再转换。

**为什么补全不直接转换：** 选中候选后，用户可能还要补参数或修正表达式。因此“填入候选”和“提交解析”分开，避免补全改变输入模式。

**为什么使用 LSP 而不维护完整命令表：** 函数、符号、用户定义属于 Typst 的语言知识；借用 Tinymist 能减少重复维护。少量本地模板只负责编辑器特有的空槽操作。独立 LSP 会话是针对一致性问题的回退办法，不是已经证明最快的方案；防抖和单请求只是限制额外开销。

### 3.4 字符串和剪贴板

- 字符串模式中，空格和运算符作为文字；Enter 或另一个双引号结束输入。字符串槽有浅色边框。
- 命令草稿内有未闭合字符串时，Enter 先补齐引号，再次 Enter 才提交整条命令。
- 复制选区得到对应的 Typst 源码；字符串选区带必要的引号和转义。
- 粘贴进入命令草稿；已有草稿时插入光标位置。确认后才解析，取消则恢复被替换的选区。

**为什么字符串独立成模式：** 用户需要输入文字时，空格、斜杠等应当保持文字含义。显式字符串边界避免结构快捷键干扰；保留双引号语法糖能减少切换成本。

**为什么复制源码、粘贴先进入草稿：** Typst 源码能直接交给 AI、普通编辑器或其他工具。先显示粘贴内容、再确认解析，允许用户检查和修正，也避免剪贴板内容在落地时被静默转换。取消操作必须能恢复原选区，所以草稿保存被替换内容。

## 四、解析、显示字典和 Raw SVG

### 4.1 统一先生成结构树

```text
命令确认 / 导入 Typst 源码
  → typst-syntax 生成语法树
  → 按当前作用域查找已登记的可展宏，生成 MacroCall
  → 已识别结构生成可编辑节点
  → 其余节点按完整源码查询显示字典
  → 命中字典：Symbol(source, glyph)
  → 未命中：Raw(source)
```

结构和字符串按各自语法优先处理。字典参与解析器的对应分支，并可为普通 Char 提供单字符显示提示，不在整段源码上做字符串替换。已登记的可展调用生成独立调用节点；未知、不可展或不符合支持的调用形式的函数调用仍按完整源码保留为 Raw。同名绑定优先于内置结构或显示字典。

例如 `frac(dif x, 2 pi)` 保留分式和分子、分母槽，未知子表达式独立编译，不因一个 Raw 就把整个分式变成 SVG。`dif` 没有专门内置实现。

`lr`、`text` 没有专用编辑指令，按原生 Typst 调用处理。字符串输入语法糖仍保留。

**为什么先统一解析，再处理 Raw：** 先判断“整个表达式是否都认识”会让一个未知叶子拖累整个结构。之前 `frac(1,2)` 能得到分式，而 `frac(dif x, 2 pi)` 整体变成 SVG，正是用户希望消除的差异。先建立外层结构，再逐个渲染未知节点，可以把可编辑范围保留到最细的已识别层级。

**为什么未知调用保持整体：** 编辑器不知道某个函数参数的语义、数量或展开行为，强行拆解会制造看似可编辑、实际无法正确写回的结构。完整 Raw 是明确的能力边界；外层若有已知 Script 或 Frac，仍然可以编辑。

**为什么删除本地 `lr`、`text` 指令：** 名称与 Typst 自身语法重合时，编辑器自定义含义可能截获本应由 Typst 处理的调用。减少这类覆盖，有利于用户按原生语言理解行为。字符串输入模式是明确的交互语法糖，性质不同，因此保留。

### 4.2 显示字典

配置为 `config/symbols.json`：键是 Typst 源码片段，值是显示 Unicode 字符或字符串。

例如可令 `times` 显示为 `×` 或 `x`，但复制和导出仍是 `times`。构建脚本将字典嵌入 WASM，因此修改字典需要重新运行 `build.cmd`。

**为什么区分源码与显示：** 把 `times`、`>=` 等源码直接改成 Unicode 或字符串字面量，会改变用户输入的表达方式，有时还会改变语义。保存 source 和 glyph 两份属性，可以改善视觉，同时让编译、复制和导出继续使用原片段。

**为什么字典不控制编辑动作：** 如果让它顺便控制按键合并、补全或模式切换，一个显示配置就会改变输入行为。最初将其限定为只服务解析器；后续用户要求普通输入也支持单字符显示映射，因此补充了视图层查询，但仍不允许配置改写对象或控制编辑动作。

**新增单字符语法糖的原因与边界：** 常见运算符逐字输入时，也应能显示配置中的数学字形。直接在 Char 的视图上附加 `display_glyph`，就能做到 `-` 显示为 `−`，同时保持源码、撤销和相邻对象不变。查询范围严格为一个 Unicode 标量，绝不向前或向后拼接字符；多字符键仍交给解析器。草稿和字符串不采用该提示，结构快捷键继续优先。此补充取代早期“任何普通字符显示都不查字典”的绝对限制，但保留“普通输入不合并、不改对象”的核心原则。

**为什么不把所有符号都编译成 SVG：** 用户试用后认为常见算术符号用字符更自然。字典提供低成本的显示方式，Raw 则覆盖未知情况；不需要为了追求单一渲染路径牺牲手感。构建期嵌入是当前的简化选择，接受修改配置后重新编译的成本。

### 4.3 分式、换行与对齐

- 命令中的 `a/b` 按 Typst 语法生成分式。
- 同一数学层级的单个反斜杠形成换行，`&` 划分对齐槽；字符串、转义和嵌套调用中的内容不按外层对齐点拆分。
- 单列多行居中；多列按右、左交替排列，列对之间留间距。连续 `&&` 保留空槽。
- 树保存行长信息，使不同长度的行能继续以 Typst 换行及对齐语法导出。

**为什么按语法层级处理：** 同一个字符出现在字符串或函数内部时，不一定是外层分隔符。依赖 Typst 语法树划分层级，可以避免文本搜索式拆分误伤嵌套表达式。对齐规则采用 Typst 的列规则，交互则借鉴 LyX 的多槽输入，避免出现编辑器与输出语言各自一套含义。

### 4.4 Raw 的生命周期

1. 原生服务把 Raw 源码与定义写入临时 `.typ`，调用 Tinymist 内含的 Typst 编译器生成 SVG；结束后清理临时文件。
2. 浏览器按“定义、公式模式、Raw 源码”缓存结果，最多同时进行两个普通 SVG 请求。
3. SVG 只是 Raw 的显示内容，原树仍保存源码。浅色边框与最小尺寸使空 SVG 也可见。
4. 成功的 Raw 按整体跨过、选择和删除，不在 SVG 内定位光标，不使用 Tinymist 的源码反向定位。
5. 失败时保留源码：从左侧按右键进入源码开头，从右侧按左键进入末尾；也可点击编辑按钮。Enter 确认后重试，Esc 恢复。

**为什么 SVG 作为原子显示：** 用户明确接受“整个删掉”，并希望每个 SVG 对应一段命令。这样无需维护 SVG 内部坐标到源码的反向映射，也不用在编译结果变化后重建内部光标关系。代价是成功的 Raw 内部没有结构化编辑槽。

**为什么失败块可进入：** 编译失败意味着还需要修改源码，不能只留下不可操作的错误预览。借用字符串式的边界进入体验，让修复动作继续使用熟悉的方向键和命令草稿；暂不为此引入庞大的通用块类型体系。

**为什么加浅框和最小尺寸：** Typst 允许产生空或极小的 SVG。没有范围标记，用户会以为对象不存在，导致光标移动和删除行为难以理解。边框表达的是“这里有一个对象”，不是最终文档的排版装饰。

**为什么缓存渲染状态而不写进文件：** SVG 可以由源码重新生成，错误状态也会随定义或编译环境变化。把它们当作派生数据，可避免再次出现两份文档需要同步的问题。

## 五、limits：Typst 决定位置类别，编辑树保持不变

### 5.1 触发条件

查询入口是编辑树中的上下标 `Script`，不先判断 operator。

原因：Tinymist 语义高亮里的 operator 包括算术符号、上下标标记等，不是可靠的数学 limits 分类。Typst 也允许通过 `limits(A)` 强制普通字母使用 limits，或通过 `scripts(sum)` 强制求和符号使用右侧附件。

当前仅查询顶层 Script，且中心槽非空、分支内没有未确认草稿。嵌套分支暂保持原布局，避免在缺少真实嵌套样式时错误判断。

**为什么接受对所有符合条件的 Script 查询：** 前置 operator 判断本身就需要可靠的求值结果。再做一个不完整的筛选既重复工作，又会漏掉显式 limits 或由定义产生的对象。直接把问题交给 Typst，语义更完整；额外调用量用缓存和防抖控制。

**为什么暂限顶层：** `sum_i` 放进分母或另一个上标后，数学样式可能改变。只有整条公式的 display 布尔值，不能代表任意嵌套位置。当前限制是为了明确正确性范围，不是声称嵌套附件不需要 limits。

### 5.2 查询算法

```text
顶层 Script 的完整 Typst 源码 + 前置定义 + 行内/行间模式
  → /api/attachments
  → 原生适配器用 Typst 求值
  → 从文档内容提取唯一顶层 EquationElem，保留外层样式
  → resolve_equation 生成数学 IR
  → 找到对应的 ScriptsItem
  → 读取上、下附件位于中心还是右侧
  → 前端调整槽位布局
```

上标分别读取 `top` / `top_right`，下标分别读取 `bottom` / `bottom_right`；返回 `limits`、`scripts` 或 `null`。不在编辑器中复制 `Never / Display / Always` 的策略，不依赖名称硬编码。

只允许解包可对应到一个外层 Script 的单元素分组，不递归捞取中心对象或附件内部的另一个 Script。出现无法一一对应的合并附件、左附件等情况时返回不支持，保留原编辑结构。

**为什么接数学 IR，而不只读取 `limits: true`：** 实际位置不只取决于某个字段；Typst 还处理字符数学类别、样式、显式覆盖和附件合并。读取已经解析好的位置，才能复用完整策略，而不是在适配层再实现一次。

**为什么没有采用 MathML 探测方案：** 曾考虑从 MathML 的上下/右侧标签反推结果，但那会引入另一种导出路径和探测约定。用户选择直接接内部库，使结果来自同一数学 IR，避免为了省接口而增加探测机制。

**为什么不能随便找一个 ScriptsItem：** 函数或中心对象内部也可能包含上下标。把它误当成编辑器的外层分支，会把合法的坐标结果应用到错误槽位。无法建立对应关系时，宁可回退，也不猜测。

### 5.3 异步与回退

- 约 160 ms 防抖，单个附件请求在途；按完整分支、定义、display 模式缓存。
- 光标移动不改变请求内容，不重复求值；响应按请求键保存，避免旧结果覆盖新分支。
- 查询未完成、不可用或失败时暂用右侧布局。底部显示附件连接、等待、成功或失败状态。
- 位置结果不写回源码、不改变 Rust 树，也不产生一条撤销记录。

**为什么布局结果不改树：** limits 与 scripts 是同一组中心、上标、下标槽的不同摆法，不是两种用户输入对象。把视觉切换做成树转换，会干扰光标、选区和撤销；保持同一树可以让异步结果只更新显示。

**为什么先允许右侧回退：** 查询不应阻塞打字，且用户输入中间态可能暂时不能求值。代价是请求完成后可能发生位置变化，所以必须明确显示查询状态。此前只把失败藏在悬停文字里，造成“是不是把 operator 当普通字符了”的误解，现已补充底部状态。

中心对象先显示 SVG 不会阻止查询。例如 `lim_(x->oo)` 的 `lim` 可以单独显示 SVG，同时整个 Script 的原始源码仍送入附件适配器。

边界示例：`limits(A)_i` 有外层 Script，会查询；`limits(A_i)` 是一个未知函数调用 Raw，其内部没有可编辑的上下标槽，不发起此类查询。

### 5.4 已修正的问题

最初把整个求值模块内容再次包成公式，导致公式外空行形成额外数学 IR 对象，使“单个上下标分支”检查失败。现改为沿 `SequenceElem`、`StyledElem` 提取真正的 `EquationElem` 并保留样式。

用户在该修正后确认 limits 功能成功。新增了 `lim_(x -> oo)` 在空定义、空行和前置定义下的回归用例；新增用例未由助手执行，不将手动反馈等同于完整测试通过。

## 六、stretch：复用 Typst 的测量和字形伸展

1. 在已经解析的 Script 中检查中心字形的显式水平 stretch 属性，不通过函数名称筛选。
2. 调用 Typst 正常的 Script 布局：先测量正上、正下附件的宽度，再由 Typst 设置中心字形的伸展参考宽度。
3. 复用同一个数学 IR 中心对象，生成只包含中心字形的 SVG，并返回其宽高。
4. 浏览器更新原子中心对象的显示，上下标仍是原来的可编辑槽，源码和光标边界保留。

不自行拼接箭头，不用 CSS 横向拉扁普通 SVG，不反查 SVG 对应的源码位置。独立的、没有外层上下标的 `stretch(...)` 仍按普通 Raw 编译。

固定 Typst 源码只增加一个小的 `editor_math_frame` 访问入口及导出，入口调用已有数学布局代码。适配器不维护另一套 limits 或字形伸展算法。

**为什么 stretch 不能只靠普通 SVG 预览：** 单独编译中心箭头时没有附件宽度，无法知道要伸展到多长；简单拉伸图片也不等于字体的数学字形伸展。必须在包含附件的布局上下文中测量，再生成中心字形。

**为什么不把整个 Script 变成一张图：** 用户需要继续编辑上下标。只取伸展后的中心 SVG，就能复用 Typst 的字形能力，同时保留结构输入槽。

**为什么允许小型 Typst 补丁：** 所需的布局能力已存在，只是入口未公开。开放访问入口比复制字体布局算法更容易保持一致；代价是升级固定版本时需要检查内部 API 兼容性。

## 七、前端如何计算坐标

**Typst 返回位置类别；浏览器决定输入槽的具体像素坐标。当前没有导入 Typst 最终附件坐标。**

| 对象 | 布局算法 |
|---|---|
| 普通右侧上下标 | 横向 Flex 放中心对象和脚本列；脚本列用纵向 Flex 放上下标 |
| 至少一个附件为 limits | 三行两列 Grid；中心在第二行第一列，正上/下限在第一/第三行第一列 |
| 混合附件位置 | 中心附件在第一列，右侧附件在第二列 |
| 分式、根式、矩阵等 | 对应的 DOM 与 CSS 结构决定尺寸和排列 |

当前上下标字号约为父级字号的 70%；limits Grid 行间距 `0.06em`，列间距 `0.04em`。实际宽高还受文字、SVG 尺寸、行高、边框、留白和空槽最小尺寸影响。

浏览器完成排版后，`getBoundingClientRect()` 测量每个光标停靠点。测量结果回传 Rust，供方向键在目标槽中寻找合适的横向位置；鼠标点击按距离选择停靠点；屏幕光标按当前停靠点矩形绘制。

因此：改变槽位距离、大小和对齐通常修改 `web/style.css`，必要时调整 `web/app.js`，刷新即可，不需要重编 Rust。改变 Typst 查询语义、编辑树或键盘操作，则需要修改对应 Rust 部分并重新构建。

目前没有复刻数学基线、斜体修正和精确上下标位移等完整排版度量。stretch 字形来自 Typst 的真实测量，但周围槽位依然由浏览器近似排版。

**为什么具体坐标交给前端：** 当前目标允许近似排版，浏览器又已经知道输入槽、边框、草稿和字体的实际尺寸。让 CSS 排列这些可编辑对象，再测量光标位置，比强行把最终排版坐标搬回编辑界面更直接，也方便独立调整视觉。

**为什么只测量、不用测量结果反复摆放：** 布局先完成，测量再服务于交互，可以避免编辑树依赖屏幕尺寸。大小变化时只需更新停靠点，结构路径不变。精确 Typst 坐标不是当前的隐藏实现，而是尚未做的另一项工作。

**接受的代价：** CSS 近似可能使脚本抬升、基线或中心视觉有偏差；这类问题首先检查前端布局，不应为了修正几像素位置去重写 Typst 的 limits 策略。

## 八、构建、启动与版本管理

| 脚本 | 当前行为 |
|---|---|
| `build.cmd` | 构建 release WASM，复制到 `web/core.wasm` |
| `build-native.cmd` | 准备固定 Typst 源码，构建 debug 适配器 |
| `start.cmd` | 缺少 WASM 时补建，构建适配器，再通过 Cargo 运行 debug 服务 |
| `build-release.cmd` | 构建 WASM、准备 Typst、构建 release 适配器和服务，并检查输出 |
| `start-release.cmd` | 仅检查并启动 release 产物，不编译、不下载 |

Release exe 位于 `target/release/lyx-typst-demo.exe` 和 `target/adapter/release/lyx-typst-layout-adapter.exe`。适配器路径跟随服务的 debug/release 模式。

批处理调用另一个 `.cmd` 必须使用 `call` 才能回到父脚本继续执行；release 脚本已补上。这些 release 脚本修订在此前阶段未由助手执行；宏阶段后来执行了 Cargo 核心测试和 WASM 构建，但没有据此验证完整 release 脚本链路。

删除本原型的 `target` 不会删除源码或文档，但会删掉 Typst checkout 和原生产物，之后需要重新准备和编译。`web/core.wasm` 不在其中；要全量重建可以运行 `build-release.cmd`。保留两个 `Cargo.lock`。

版本来源分三处：

- 编辑语法库由原型 `Cargo.toml` 的 `typst-syntax.rev` 固定。
- limits/stretch 引擎由 `native-adapter/prepare.ps1` 的 revision 固定；当前为 `59b5999da8e74e74583069408d2564fc1f9bc973`。重复构建不会自动升级；已有 checkout 版本不匹配时脚本报错。
- LSP 和普通 Raw SVG 使用实际找到的 Tinymist。可通过 `TINYMIST_BIN` 指定固定版本，避免随编辑器扩展更新而变化。

`prototypes/lyx-rust` 不依赖父目录旧原型的源码或外部 LyX checkout。构建仍依赖 Rust、Git、依赖缓存或网络，运行依赖 Tinymist。当前原生服务嵌入构建时的项目路径，移动目录后需要重新编译，尚不是可任意移动的单 exe 包。

**为什么区分构建和启动：** 用户希望编译一次后直接使用。通过 exe 启动不应再调用 Cargo 或准备源码；开发用 start 与纯 release 启动分开，是对这个需求的直接回应。debug/release 和 WASM/native 是两个不同维度，不能把它们混成同一套目录含义。

**为什么固定版本并保留锁文件：** limits/stretch 使用内部 API，静默升级可能改变行为或破坏适配入口。固定 revision 让升级成为主动操作；锁文件稳定其余依赖。Tinymist 是另一个外部程序，因此还要单独控制，不能把固定内部 Typst 误认为固定了所有编译路径。

**验证分工的演变：** 此前阶段曾由用户执行构建和运行；宏阶段助手随后执行了本地核心测试与 WASM 构建。用户明确要求不要使用 computer use，界面由用户测试。收尾记录须分别列出自动测试、构建、用户反馈和未执行的检查，不能沿用此前“全部未经测试”的笼统描述，也不能声称已完成浏览器或完整原生服务验收。

## 九、宏管理器：可展性、嵌套模板与缓存

### 9.1 分类依据的演变

此前为明确编辑器与 Typst 的职责，曾移除本地宏展开。宏管理阶段重新提出了显示展开和多处参数框联动的需求，最初拟按“编辑器创建／代码创建”分类；讨论后改为按“能否结构化展开”分类。

**最终决定：** 创建来源不影响分类，两类定义都使用原生 `#let`，也不添加自定义注释标记。宏体可投影为结构，且每个参数引用都能落到可编辑位置时，才登记为可展。不可展宏保留源码作为上下文，其调用交给 Typst 编译。

**为什么不能只检查宏体有没有 Raw：** 不含参数的 Raw 可以独立编译，外围结构仍可编辑。真正阻断参数框映射的是参数进入 Raw。当前支持范围还要求直接返回数学公式，以及可识别的位置参数；未显示的参数、默认／命名／可变参数和动态宏体不会仅凭“未发现 Raw 参数”就被判为可展。

参数引用按 Typst 语法节点识别，不做字符串替换。尤其是单字母 `x` 在数学模式下是字母；引用参数应写 `#x`，多字母数学标识符可以直接引用。早期讨论中裸 `x` 的示例已据此修正。

### 9.2 UI、源码和编辑行为

在原公式编辑框下增加 `let` 源码列表，不创建另一个原型，也暂不提供可视化宏定义编辑器。

- 列表支持添加、编辑、删除，显示可展判定及原因；被后续同名定义覆盖的条目另有标识。
- 输入只修改草稿，点击“应用修改”或 Ctrl+Enter 后生效。语法错误保留草稿和上次有效定义；公式中的命令草稿须先确认或取消。
- 已应用的宏定义变化参与公式的撤销／重做；导出仍是前置 `let` 加一个公式。
- `MacroCall` 只保存名称和一份实参槽，不保存展开后的公式。固定宏体在调用处不可编辑；需要修改定义时回到源码列表。
- 同一实参的所有显示入口共享一个槽位，颜色按参数序号在六色中循环；修改任何入口后其他位置跟随视图更新。不同调用的实参彼此独立。
- 光标同时保留规范的槽位路径和显示位置 `occurrence`，使点击第二个重复框后，输入不会跳回第一个框。
- 整体复制、删除和导出以调用为单位；参数框内的选择操作针对实参。参数槽起点退格先选中整个调用，不把宏体摊平成普通公式。

**为什么共享槽位：** 为每个显示位置保存一份实参，再同步修改，会增加撤销、选区和漏同步的风险。一份实参配多个入口，使联动成为重新生成视图的结果。

### 9.3 按定义顺序登记，保留名称与版本

| 结构 | 内容与职责 |
|---|---|
| `Vec<MacroDefinition>` | 按源码顺序保存定义、分析结果和共享模板 |
| `HashMap<String, Binding>` | 当前名字对应可展定义，或不可展绑定 |
| `Rc<MathData>` | 共享不可变模板；WASM 编辑核心单线程，采用 `Rc`，不需要 `Arc` 的跨线程引用计数 |
| `TemplateCall { definition }` | 模板中的调用边，按定义序号引用当时登记的版本 |
| `Parameter { index }` | 模板中的参数引用；实例化视图时映射到调用的真实实参槽 |

**为什么不可展宏也登记名字：** 如果后面用不可展定义重新绑定 `pd`，后续宏不能继续把这个名字解析为旧的可展 `pd`。因此不可展宏无需生成模板，但不能从名称表中消失。原始源码仍按顺序交给 Typst。

**为什么不能只按名字查最终定义：** `jac` 在定义时捕获了当时的 `pd`。后来新增另一个同名 `pd`，不能反过来改变先前 `jac` 的模板。嵌套调用引用具体定义版本，最新名称表只负责分析当前及后续源码。这里“新增后续同名定义”和“编辑原定义”不同：编辑原定义后，后续宏会重新分析并捕获新版本。

模板边只指向此前已登记的可展定义，不在登记时复制整个展开结果。函数参数会遮蔽同名宏；具名函数自身的递归引用不会错误绑定到旧的同名定义。当前不对尚未登记的前向调用做补解析，也不提供递归函数的结构化求值。

### 9.4 从 `pd` 到 `jac` 的参数映射

```typst
#let pd(f, x) = $frac(partial #f, partial #x)$
#let jac(f1, f2, x1, x2) = $mat(pd(#f1, #x1), pd(#f1, #x2); pd(#f2, #x1), pd(#f2, #x2))$
$ jac(f, g, x, y) $
```

第一版曾把 `pd` 判为可展、`jac` 判为不可展。原因是在分析宏体时没有传入可展宏表，四个 `pd(...)` 都落成了带参数引用的 Raw，**不是达到最大递归深度**。现已改为先登记 `pd`，再分析 `jac` 时引用其模板。

例如 `pd(#f1, #x2)` 将 `pd.f` 映射到 `jac.f1`、`pd.x` 映射到 `jac.x2`。多层引用逐层组合后，显示颜色与编辑目标都取自外层 `jac` 的实参，不取自每次内部 `pd` 的局部参数序号。

结果是四个分式、八个参数入口，但调用树仍只有一个 `jac` 和四份实参槽。参数表达式也可以包含固定结构，例如内层调用接收 `#y + 1` 时，只在属于外层 `y` 的部分提供输入框。

**作用域还影响 Raw：** 被调用模板里的独立 Raw 使用被调用宏定义处的上下文；实参表达式里产生的 Raw 使用调用它的宏定义处上下文。把所有 Raw 都放进最终定义上下文，会使后续同名绑定错误地影响旧模板。

### 9.5 当前更新算法：全量解析源码，增量更新模板

当前没有实现完全增量编译。一次应用宏修改时，各层工作如下：

| 阶段 | 执行范围 |
|---|---|
| 列表输入 | 只保留草稿，不进行宏分析 |
| 定义源码解析 | 全量调用 Typst 语法解析器，得到整段定义的语法树 |
| 顺序登记 | 扫描整个定义列表，重建当前名称表 |
| 可展判定与模板构建 | 复用源码未变的前缀，从第一条变化处重建后缀 |
| 当前公式 | 通过源码整体重新解析，重新判定调用是否可展；保留调用及实参，光标回到起点 |
| 普通公式输入 | 复用当前定义集缓存，修改实参并重新生成显示视图 |

举例：100 条定义中修改第 90 条，整段定义源码仍会被解析和扫描；前 89 条的模板复用，第 90～100 条重新分析。后缀中没有直接依赖第 90 条的宏也会重算。插入、删除同样以第一处变化为界。

**为什么先采用后缀更新：** 定义顺序、同名覆盖、参数遮蔽和上下文都可能影响后续分析。从变化处重建后缀，容易保证语义一致，也能复用前缀的共享模板。只按直接调用关系失效更精细，但必须同时记录名称解析和上下文依赖，当前规模下先不增加这套机制。

缓存只保留当前定义集，不无限积累每一次修改的版本。撤销恢复源码和调用树后，模板按恢复的定义集重建或复用。全量源码解析、名称表扫描和公式整体重新解析的开销依然存在，不能将“模板增量更新”描述成“只处理变化的那几行”。

### 9.6 展开规模保护与性能记录

嵌套模板组成共享依赖图。即使登记时不复制模板，显示时重复调用仍可能产生指数数量的节点。模板登记时预先组合固定节点量和各参数的重复次数，用饱和计数估算显示规模，避免预估本身逐路遍历整个依赖图。

显示预估超过 4096 个结构节点，或触发深度保护值 64 时，回退到调用名及可编辑实参。**可展性属于结构判定，预算限制属于显示策略**；达到预算不会把列表中的宏改成不可展。

本机一次 Node/WASM 测量采用 100 条定义、一个调用：导入约 2.64 ms；预热后 200 次方向键操作，中位数约 0.18 ms，P95 约 0.24 ms。测量包含 JSON 接口和 Rust 视图生成，不包含浏览器布局、绘制、SVG 编译或 LSP 延迟。它用于说明当前规模下的核心开销，不是端到端性能保证，也没有据此证明无需进一步优化。
